## 2. 当前极光是什么类型的模组

极光已形成一个独立维度探索模组的基础：环境、材料、建筑与家具内容丰富，另有净化仪式、月之护盾、赐福、饰品、特殊状态和 Boss 战。整体仍属于 Alpha 阶段，功能完成程度不一致。

当前技术基础为 Minecraft 26.1.2、NeoForge 26.1.2.84、Java 25、GeckoLib 5.5.2，模组命名空间为 `theaurorian2`，版本为 `0.1.0-alpha.1`。

旧极光主要作为美术与设计来源。当前项目中仍有显式的 Legacy 注册与占位实现，不能根据物品名称、模型或创造栏条目，推断其旧版功能已迁移。

## 3. 各系统的实际职责

| 系统 | 目前已有的实现 | 理解与扩展时的重点 |
| --- | --- | --- |
| 维度与旅行 | 独立维度、噪声地形、天空与时钟；达到铁器进度后睡醒获得卷轴，卷轴负责往返、战斗限制和返回位置 | 涉及玩家附件、世界存档与安全落点，不能只修改物品类 |
| 群系与自然生成 | 平原、薰衣草、谧木与幽帘森林、咒霜森林、雪地、海洋、河流、洞穴、空岛、彼岸花岛等 23 份群系定义 | 群系文件数量包含丘陵等变体；自然生成还依赖维度噪声选择、标签和 biome modifier |
| 地下与遗迹 | 自有矿石、晶洞、地下城、大小遗迹、矿井、空岛群结构、幽暗迷宫 | 同时使用原版生成器、自定义 Feature、NBT 模板和代码生成的结构，入口不只有结构 JSON |
| 生物与 Boss | 四种极光动物、蜘蛛母体及其幼体、卵和投射物，另有 NPC 与训练假人 | 蜘蛛母体已有较复杂的战斗阶段和场地控制；NPC 的存在不代表完整任务系统 |
| 净化与月之护盾 | 仪式确认、持续仪式、怪物波次、失败与完成处理、净化状态、护盾吸收和恢复 | 涉及方块实体、网络、玩家数据、效果、音乐与 HUD，需要一起看 |
| 赐福与占星 | 五类赐福轮换、预报、占星界面；赐福影响部分战斗、生存和采集行为 | 服务端判定效果，客户端负责显示；不是单纯天空换色 |
| 饰品与遗物 | 24 格饰品栏、遗物旋转与相邻强化、属性与特殊效果 | 对原版背包做了扩展；读档、死亡、换装、同步是关键边界 |
| 状态与附魔 | 腐化、结晶化、压力、禁咒等状态机制；5 份实际附魔定义 | 有些附魔只有预留键；腐化等机制还涉及延后结算与装备状态 |
| 工具与装备 | 木石工具模型、骑士与游侠装备、特殊武器、模型物品 | 普通装备属性、GeckoLib 显示与特殊攻击逻辑分布在不同文件 |
| 建筑与家具 | 五木色箱子、储物桶、两类板条箱、桌椅凳、长凳、小桌、镜子、盛水容器、木匠工作台等 | 同外观系列尽量共用行为；同名近似物件仍可能有不同玩法 |
| 客户端表现 | 自定义实体与方块实体渲染、界面、粒子、音乐、草色、实时镜面与光影兼容边界 | 复杂视觉功能跨越模型、渲染状态、缓存和资源重载，不能用文件数判断是否过度实现 |

目前资源中的自然怪物生成列表普遍较空，四种动物出现在部分地表群系；Boss 与仪式生成的敌人另走代码。世界资源丰富，不等于完整的自然生物生态已经填满。

## 4. 哪些已经实现，哪些还属于准备内容

已经有明确玩法实现的包括：卷轴往返、净化仪式、月之护盾、赐福、饰品强化、蜘蛛母体战斗、可坐家具、容器储物、盛水容器与镜面反射。

仍需按当前代码区分的内容：

- 木匠工作台明确是双格装饰方块，制作功能尚未赋予，符合此前“作用之后再说”的要求。
- 皎月箱保留在导出与建模方案中，不能算作已经注册完成的正式箱子。
- `ModLegacyItems` 中不少条目通过普通 `Item` 注册；有模型、有翻译或被归入“装备”分类，不代表具备该名称暗示的特殊机制。
- `ModEnchantments` 的预留附魔键多于目前实际存在的 5 份附魔数据；文档中的旧版附魔清单也是设计库存。
- `IserynValeEntity` 有实体、显示名称和属性，但没有完整的目标行为与对话任务实现。
- 女王相关进度数据等接口已经存在，不能因此认定完整女王战、剧情路线和结局已经实现。
- 破坏掉金苹果的板条箱仍使用测试掉落，这是用户确定的测试用途；它和储物板条箱属于两种功能。

剧情真相、教会宣传与未定设计仍以 `LORE_CANON.md` 为准。本报告描述实现状态，不补写剧情设定，也不把设定文档当作已完成的游戏功能。

## 5. Java 与 JSON 如何配合

普通方块通常需要串起：注册项 → 方块状态 → 模型 → 贴图，以及物品显示、语言、配方、掉落和标签。带存储、坐乘、动画、两格结构的方块还会增加对应行为与渲染支持。

自然生成通常需要串起：维度的群系选择 → 群系或 biome modifier → Placed Feature → Configured Feature → 原版/自定义生成器 → 方块或结构模板。部分资源也会由树苗、骨粉和 Java 直接引用。

模型系统并不只有一种：普通 JSON 模型、OBJ 蘑菇模型、GeckoLib 几何与动画、Java 模型，以及由 JSON 读取的自定义箱子几何都存在。它们服务于不同需求，不能为减少文件随意互转。

本轮资源检查结果：

- 4,307 个正式 JSON 均能解析，没有发现重复键；40 个 `.mcmeta` 也能解析。
- 中英文语言键集合一致，各 1,074 个。这不代表所有文案语义都已校对。
- 扫描了 7,536 处本命名空间模型或贴图引用；纳入图集别名和 OBJ 路径规则后，本次检查范围内没有剩余的缺失引用。
- 箱子物品模型的 `block/*_chest_model` 是由图集映射到 `entity/chest/*` 的贴图名称，不需要同名的方块 PNG；不能按直接文件路径误删或误报。
- 存在 96 组语义完全相同的 JSON。相同内容可能分别对应不同注册项、状态、标签和用途，**不能据此认定可删除**。

JSON 语法通过不等于所有 Codec、方块状态组合、动态引用、动画或世界生成结果都正确；这些仍需要针对性的运行验证。

## 6. 当前做得比较好的地方

- 注册、通用逻辑与客户端实现基本有清晰的目录划分，常规行为大量复用原版与 NeoForge 机制。
- 家具通过共用方块类、成对家具基类和座位实体复用行为；不是每种木材复制一套交互逻辑。
- 多种玩家状态使用附件，世界级状态使用 SavedData；网络请求有服务端处理与必要校验。
- 重要维度相关规则有范围判断，避免把极光矿井、天空等规则直接套到所有世界。
- 谧木箱的改名为旧 `aurorian_chest` 注册名保留了别名，体现了存档迁移意识。
- 镜子已有可见性、数量、分辨率与缓存方面的控制。仍需实测性能，但已有控制成本的设计。
- 模型导入脚本多有几何、UV、调色板断言，PowerShell 包装入口使用 `json_utils.ps1` 校验压缩输出。

## 7. 已确认的问题与维护风险

### 优先处理：饰品读档时过早触发同步

现有无光影和有光影两份测试日志都记录了 `accessory_inventory` 反序列化失败并跳过附件。直接异常为 `player.connection` 为空。

当前调用链为：

`AccessoryInventory.deserialize()` → `finally` 中的 `setChanged()` → `AccessoryEffects.reconcile()` → `MoonShieldSystem.reconcileMode()` → `getData(MOON_SHIELD)` → 创建/同步附件时访问尚未建立的玩家连接。

这说明读档恢复与联网同步的时机混在一起。即使护盾最终不需要切换模式，首次读取可同步附件也可能触发同步。它可能影响饰品库存的正常恢复，优先级高于整理重复文件。尚未用专门的带饰品旧存档验证物品损失范围，不能声称所有存档都会丢饰品。

证据位置：

- `src/main/java/cn/teampancake/theaurorian2/common/inventory/AccessoryInventory.java:56`
- `src/main/java/cn/teampancake/theaurorian2/common/inventory/AccessoryEffects.java:81`
- `src/main/java/cn/teampancake/theaurorian2/common/world/MoonShieldSystem.java:70`
- 已有日志 `build/mirror-no-iris-check.log:620`、`build/mirror-iris-release-check.log:1715`

后续修复应把纯数据恢复与登录后的效果重算、同步分开，再验证重登、死亡、保留物品规则和旧存档。

### 已确认：森林生成脚本与当前资源不一致

当前 `silent_tree.json` 与 `curtain_tree.json` 的生成类型都是 `minecraft:tree`，包含实际树形配置；`generate_forest_resources.ps1` 第 441、516 行附近却会把这两份文件写回 `theaurorian2:silent_tree` / `theaurorian2:curtain_tree`，配置为空对象。

因此直接重新运行旧脚本会改变当前树木生成行为。脚本并非当前全部资源的可靠再生成来源。应该先核对生成目标与现行结果，再恢复可重复生成能力；不能为了“统一”而把当前树形退回旧版。

### 兼容风险：原版配方同时存在覆盖和动态修改

项目在 `data/minecraft/recipe` 下覆盖了 40 份原版配方，又通过 `AurorianRecipeIntegration` 修改这批配方中的木棍材料，使谧木木棍能够参与合成。

功能意图明确，但整份覆盖扩大了与其他模组、数据包修改同名配方时的冲突范围。后续可验证是否能保留相同行为并减少覆盖；本轮没有做跨模组冲突复现，也没有更改配方。

### 工程风险：测试尚未形成稳定的自动回归

Gradle 有 GameTest 运行配置，但正式源码中未发现实际 GameTest 或单元测试；GitHub 工作流只执行构建。已有本地验证与导入断言有价值，但无法自动证明饰品读档、双格拆除、容器容量和镜面重载持续正确。

后续应优先把涉及存档和交互的关键用例固化，不需要给每种颜色或静态模型重复写测试。

### 工程风险：历史资源入口多，部分脚本依赖本机路径

木箱有旧版、无锁版、换色版和 Wooden Pack 现行方案；木凳、长桌也有被替换的方案。多个脚本仍指向下载目录、旧项目目录或固定 Python 路径。

这主要影响另一台机器重新生成素材与维护时选错入口；已经放入 `src/main/resources` 的资源不依赖这些下载目录才能在游戏中使用。

### 维护风险：复杂逻辑集中

`UmbraDarkMazePiece` 约 1,981 行、`SpiderMotherEntity` 约 1,558 行，`ModStructureBlocks` 1,055 行、`ModBlocks` 987 行；效果结算和仪式也各有较大类。

这说明修改时需追踪更多关联，不等于文件大就有性能问题。后续应围绕实际职责和可验证边界拆分，不能按行数强行合并或改写。世界生成、仪式波次、Boss 战和镜面渲染值得做性能测量，本轮没有据此判定必然卡顿。

## 8. 后续批量扩展时采用的依据

五木材的语义映射应保持一致：

| 木材 | 常见家具 ID 前缀 | 木板采色来源 |
| --- | --- | --- |
| 谧木 | `silent_wood` | `silent_tree_planks` |
| 垂柳木 | `weeping_willow` | `weeping_willow_planks` |
| 幽帘木 | `curtain_wood` | `curtain_tree_planks` |
| 咒霜木 | `cursed_frost_wood` | `cursed_frost_tree_planks` |
| 污秽木 | `filthy_wood` | `filthy_tree_planks` |

同系列保留相同模型、UV、纹理结构与功能，仅替换要求改变的材质色阶。包带、金属和工具附件按该系列最终要求处理：例如铁匠储物桶的箍带保留原材质，不能套用所有家具都采树皮色的旧规则。

可以复用现成的成对家具放置、坐乘、储物和盛水交互。必须保留实际差异：小容器与大容器容量、瓶装水与桶装水、可破坏战利品箱与储物箱、横向双格与竖向双格都不是单纯换名。

新增内容需要同时核对注册、物品显示、方块状态、模型、贴图、翻译、配方、掉落、标签、创造栏；特殊功能再核对实体、方块实体、网络、渲染和存档。重复的是资产装配步骤，共用行为已存在时无需再复制一套 Java 实现。

总体判断：现有结构足够支持继续扩展，尤其是五木材家具系列。下一步最值得补的是数据安全和生成流程的一致性，使新增内容不会破坏已经确认的效果。
